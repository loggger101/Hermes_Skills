# Skill invocation conventions: model-invoked vs user-invoked, and how skills call each other

Source: [mattpocock/skills](https://github.com/mattpocock/skills) `.agents/invocation.md` (MIT) plus its `CHANGELOG.md` entries for
1.2.x-1.3.x (PRs 878, 880, 551, 766), read 2026-10-05. Source-read; the harness behaviours quoted (Codex filtering, the Skill tool)
are upstream's findings, not re-tested here. The Hermes mapping at the end is this repo's own practice.

## The one axis: who can reach a skill

| Kind | Reachable by | How it is declared (upstream) | The `description` is written for |
|---|---|---|---|
| **user-invoked** | only the human typing its name | `disable-model-invocation: true` in `SKILL.md` frontmatter (Claude Code); `policy.allow_implicit_invocation: false` in `agents/openai.yaml` (Codex) | a person browsing a list: one plain line |
| **model-invoked** (default) | the model or the user | omit both settings | the model: rich trigger phrasing ("Use when the user wants..., mentions..., asks for...") so auto-invocation fires |

Each harness removes a user-invoked skill from the model's reach in its own way, so nothing but the human can fire it, and **no other
skill can**: a user-invoked skill may call model-invoked skills, never another user-invoked one.

Codex gotcha found upstream (changelog 1.2.2): setting `policy.allow_implicit_invocation: false` on a skill that should be
model-invoked made Codex filter it out of the model-visible list, so its description could never trigger it and only an explicit
`$skill` call worked. The fix was to drop the policy block and move the skill to the model-invoked list in the READMEs.

## How one skill tells the agent to run another

1. **Say it as a tool call, naming the tool**: `Call the Skill tool with "grilling"`. A bare mention ("run the `/grilling` skill") does not
   reliably cause the skill to load; upstream calls this the documented rough edge behind its most-reported problem. Deep
   `../other-skill/FILE.md` links are discouraged for the same reason.
2. **One skill per call.** A step that needs two skills says so as two calls: `Call the Skill tool twice, for "grilling" and
   "domain-modeling"`, not "call it with X and Y" (which reads as one call taking both).
3. **Only for operative instructions.** Router prose that lists skills for a human to choose from keeps plain `/skill` labels; only a
   skill's own "go run this now" steps use the Skill-tool wording.
4. **Only when the target is model-invoked.** If a step's precondition is a user-invoked skill (for example the setup skill), the
   skill must instead **tell the user** to run it; it cannot call it, even by naming it to the Skill tool. Upstream removed such
   preconditions from `to-spec`, `wayfinder`, `to-tickets`, `triage` and `code-review`, and changed `diagnosing-bugs`' post-mortem so an
   unattended bug-fixing flow no longer tries to hand off to a user-invoked skill (it would fail with nobody to catch it).

## Passive vs active domain work

Merely **reading** the glossary (`GLOSSARY.md`, renamed from `CONTEXT.md` in 1.3.0) for vocabulary is a one-line prose pointer, not a
skill call. Only the active discipline of challenging terms, testing edge cases, writing ADRs and updating the glossary inline is the
`domain-modeling` skill. Do not load a heavy skill to look up a word.

## Mapping to this repository

- This repo's skills name each other with `skill_view(name='X')` and list them in `related_skills`, which the pointer gate
  (`tools/verify-all.py`, "skill pointers") checks resolve; follow the same rule 1-2 spirit: name the loader, one skill per call,
  and keep every named skill in `related_skills`.
- The router (`skill-flow-router`) is the "router prose" case: it may list skills as labels.
- There is no frontmatter switch here for user-invoked skills; treat a skill that must not auto-trigger as one whose `description` says
  "only when the user asks for X" and keep it out of other skills' operative steps.
- The `agents/openai.yaml` sidecar is Codex-specific and is not generated by this repo's plugin tooling.
